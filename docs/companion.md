# Connected companion guide

The **Tools** hub contains four essentials: Hero picker, Hero pools, Compare matches and Hero reference. Personal analysis is in Progress, the notebook is in Matches, and setup is in Account. They use the existing glass interface, dark/light themes, shadcn/Base UI primitives and English/Spanish copy catalogs.

## Keys and provider costs

Existing Steam/OpenDota configuration remains unchanged. No new paid infrastructure is needed. `OPENDOTA_API_KEY` is optional for the existing provider client. Source requests use its shared in-memory cache, concurrency/body bounds and database daily request allowance. Valve feeds use their fixed public origin, without an OpenDota key.

`OPENAI_API_KEY` is optional. Add it only to `apps/api/.env` when enabling AI features, restart the API and reload Tito. Never put it in frontend environment variables. Saved views, pools, notes, comparison, public references, session summaries and manual drafts work without it.

Reviews, drafts and coaching share the existing estimated daily/monthly AI budget. Defaults remain $0.50/day and $5/month application estimates. Per-user UTC attempts are separate: five reviews, thirty drafts and ten coaching requests. Identical fingerprints reuse saved responses. Model errors may retain reservations. These controls are estimates rather than a guaranteed provider invoice ceiling; no provider billing settings were changed.

Coaching persists at most twenty bounded results per user. Written notes survive summary pruning and account relinking; old-account notes stay hidden until that Steam identity is relinked. Obsolete feedback-only records are reclaimed without deleting written notes. New personal tables cascade on account deletion. Verified Steam identity gates every private match association; selecting a public player never authorizes their notes, reviews or history. Schema migration `0006_remarkable_doctor_octopus.sql` adds four tables and nullable match metadata without dropping existing records. Deployment startup applies migrations through the existing PostgreSQL lifecycle.

## Local game setup

1. Run Tito locally and sign in. Open **Account → Local game connection**.
2. Choose **Create game configuration**, then download the file. The connection token stays in component memory and in the downloaded configuration; treat the file as private.
3. Put `gamestate_integration_tito.cfg` in Dota's `game/dota/cfg/gamestate_integration` directory. Set the displayed `-gamestateintegration` Steam launch option and restart Dota.
4. Check the connection. The receiver is the API's loopback HTTP port, so the game does not need to trust Portless's HTTPS certificate.
5. In the picker choose **Use revealed picks**, check the imported heroes, then request suggestions separately if desired.

The token expires after four hours or an API restart. Creating a new configuration revokes the previous one. The receiver retains only whitelisted hero/team/match fields in memory, strips player identities, and rejects contradictory teams/picks. Stale, missing-team and ambiguous five-allied-hero states cannot be imported. No game files are edited automatically, no process memory is read, and no game input is automated. Dota modes can omit draft fields; actual ranked-game payload support has not been verified.

## Offline references and deployment

The service worker is registered only after **Enable offline references**. It preloads a bundled public reference page/catalog and brand assets, and bounds opportunistic same-origin static asset caching. Private APIs, auth routes, cross-origin requests and query-bearing URLs remain network-only. Navigation falls back to the public reference page when the server cannot be reached. **Remove offline references** unregisters Tito's worker and removes its public caches; reload to release the current worker.

Serve the frontend over HTTPS (loopback localhost is allowed for development), preserve real `sw.js`, manifest, reference JSON and static asset paths before SPA fallback, and avoid long immutable caching for `sw.js`, the manifest or reference catalog. Installation availability depends on the browser/OS. This is not offline private match history.

## Verification limits

Automated coverage includes ownership/account switching, bounded concurrent writes, missing/zero data, source/cache failures, model evidence validation and spending controls. Real PostgreSQL tests cover additive/repeat migrations, concurrency and production startup. Controlled browser fixtures cover the connected tool pages and responsive glass themes.

Live OpenAI quality, latency and billed usage need verification with your provider configuration. Real in-game GSI payloads, OS-level installation and a production deployment are not claimed verified. Provider evidence may be partial, old or unavailable. Match totals and aggregate hero results cannot explain individual decisions; replay verification remains necessary.

Run `bun run check` for the current type checks, test suite, production builds and formatting. `bun run test:postgres` separately verifies the database lifecycle; `bun apps/api/src/coaching/evaluate.ts` runs controlled offline AI boundary cases.
